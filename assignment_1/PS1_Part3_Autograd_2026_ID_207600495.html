A Short Intro to PyTorch Autograd¶

In PyTorch, autograd, short for automatic differentiation, is a core functionality that empowers you to efficiently calculate gradients during deep learning model training. It acts as a computational engine that automatically tracks the operations performed on your tensors and calculates the gradients of any loss function with respect to the model's learnable parameters.

Why is Autograd Important?

  • Gradient Calculation: Deep learning relies heavily on gradient-based optimization algorithms like stochastic gradient descent (SGD). These algorithms adjust the weights and biases (learnable parameters) of your model based on the gradients of the loss function. Autograd automates this process, saving you from manually calculating complex derivatives.
  • Efficient Backpropagation: Backpropagation is the algorithm at the heart of training deep neural networks. It propagates the error (loss) backward through the network, allowing the model to adjust its parameters in the direction that minimizes the loss. Autograd streamlines this process, making training more efficient.

How Does Autograd Work?

  • Tracking Operations: When you enable autograd mode (with torch.enable_grad()), PyTorch creates a computational graph in the background. This graph tracks all the operations performed on your tensors

  • Backward Pass: Once you calculate a loss function (which typically depends on the output of your model), you can call the backward() method on the loss tensor. This triggers the backward pass through the computational graph.

  • Gradient Calculation: As the backward pass traverses the graph, autograd computes the gradients of the loss function with respect to each learnable parameter in the network. These gradients indicate how much a specific parameter contributed to the overall loss.

  • Parameter Update: By utilizing these gradients, optimization algorithms like SGD update the model's learnable parameters in a direction that minimizes the loss function. This iterative process continues until the model converges (achieves a desired level of performance).

Key Points about Autograd:

  • Automatic
  • Only for Learnable Parameters: Autograd tracks gradients only for tensors that have requires_grad=True.
  • Dynamic vs. Static Graphs (Optional): PyTorch offers both dynamic computational graphs (eager execution) and static graphs (graph mode) for model development.

1. Which method is the most accurate in finding the "true" weights? Why? Is it always applicabale? Hint - you should think about it from a statistical theory point of view.

The analytic solution $W=(X^T X)^{-1} X^T Y$ is the most accurate, because it computes the exact minimum of the MSE directly, by setting the gradient $\frac{2}{n} X^T (XW - Y)$ to zero. Gradient descent only gets closer step by step and stops when the epoch limit is reached (here all 3 GD versions reached the same weights up to 3 decimal places, because the lr and the number of epochs were enough).

From a statistical point of view, under the Gauss-Markov assumptions, OLS is the Best Linear Unbiased Estimator (BLUE): it is unbiased, and it has the lowest variance among all the linear unbiased estimators.

However, it is not always applicable:

  • $X^T X$ must be invertible. If there are more parameters than observations, or features that are exactly collinear, it is not. And when features are only highly correlated (like total_bedrooms and households here, with a correlation of 0.98), some singular values of $X$ get small. As we saw in class, OLS divides by them, so the solution becomes unstable (Ridge avoids this).
  • When the number of parameters $p$ is very large, we cannot store and invert a $p \times p$ matrix.
  • Non-linear models like neural networks do not have a closed-form solution, so we need gradient descent.

2. Why did we scale the data ? (answer with respect to the model/algorithm)

We scaled the data because the raw features are on very different scales: total_rooms goes up to about 38,000, while median_income only goes up to about 15. GD uses one learning rate for all the directions, and as we saw in class it moves fast along directions with large singular values of $X$ and slowly along directions with small ones.

Without scaling, the learning rate must be tiny so that the directions of the large features do not diverge, and then the small features almost do not move. After standardizing (mean 0, std 1) all the features are on the same scale, so one learning rate (0.1) works for all of them, and GD converges in far fewer steps.

Standardizing does not make all the directions equal, though. The features are still highly correlated (0.86 to 0.98 between the four count features), so there are still directions with small singular values, and they are learned slowly. This is why the loss was still going down between epoch 1,000 and epoch 2,000.

Scaling also puts the intercept at 0 and makes the sizes of the coefficients comparable. It does not change the OLS fit itself, only how easy it is for GD to reach it.

3. Do you think our model specification produced good results? Why or why not? Justify your answer.

The results are only moderate. The final MSE on the standardized target is about 0.43. A model that always predicts the mean would get an MSE of about 1, so our model explains only about 57% of the variance.

The main problems I see:

  • The density of the error is not symmetric: it has a long tail of negative errors, which means there are districts where the prediction is far below the real value. These are mostly the expensive districts. Part of them are the 814 districts whose price is capped at 500,001 in the data, so for them the real price is not even known.
  • The data file is sorted by longitude (the first row is at -114.31 and the last at -124.35), so the x axis of the error plot is roughly the east-west position. The errors are not spread randomly along this axis: there are whole regions where the errors go up or down together. This suggests that the location matters, and that dropping latitude/longitude took important information out of the model.
  • Because the features are strongly correlated, the coefficients are hard to interpret: total_rooms has a positive correlation with the price (+0.13), but gets a negative coefficient (-0.375) in the model.
  • We measured the error only on the training data, so we do not know how the model does on new data.

4. What can you say about the total process times between methods?

The exact times change a bit from run to run, but the order is clear. The analytical solution is by far the fastest (a few milliseconds): it is computed once, and the only matrix it inverts is 7x7. Every GD version does 5,000 passes over the 17,000 rows, so it takes a few seconds.

Between the GD versions:

  • The manual PyTorch loop was the slowest. It does the same 7 separate multiply-and-sum operations per step as the numpy loop, but on the CPU each small PyTorch operation probably costs more than the same numpy operation, and there are many thousands of them.
  • PyTorch autograd was faster than the manual PyTorch loop, even though it also builds the graph and runs backward(), because the prediction is one matrix product (tX @ tb) and the update is one vector operation instead of 7 separate ones.

5. Can you suggest some improvements to the model definition?

  • Put the location back in (latitude/longitude, or a grouping of them into areas), since the errors depend on the location.
  • Use ratios instead of raw counts (for example rooms per household, bedrooms per room, people per household). The four count features are almost the same variable (correlations of 0.86 to 0.98), and ratios should be less correlated and easier to interpret.
  • Add non-linear terms, or use a small neural network instead of a linear model.
  • Handle the capped prices, for example by removing the 814 capped districts, since their real price is not known.
  • Add regularization (Ridge or Lasso) to stabilize the coefficients of the correlated features.
  • To check that a change really helps, compare the models on a validation set (or with cross-validation), and not on the training error.

6. Can you suggest some improvements to the solution algorithm?

  • Keep the weights as one vector and compute everything with matrix operations ($XW$ for the prediction, $\frac{2}{n} X^T (XW - Y)$ for the gradient), like in 1.4, instead of 7 separate scalars.
  • Use a stopping rule instead of a fixed number of epochs: stop when the loss almost does not change. Here the loss stopped changing around epoch 3,000, so the last 2,000 epochs were not needed.
  • With a validation set, use early stopping: stop when the validation error stops improving. As we saw in class this is a kind of regularization, like Ridge: the directions with small singular values are learned slowly, so if we stop early they stay close to their starting point.
  • Choose the learning rate (and $\lambda$, if we add regularization) together, by a grid search on a validation set.
  • For larger data, use mini-batch SGD or an adaptive optimizer like Adam, and run on a GPU.
